# Token Research and Cache — October 6, 2026

## Finding

The captured data is from **Usage of an OpenHands conversation**, not Grafana. It shows input 125,088, Cache Hit 95,780, Cache Write 0, output 4,838 and total 129,926. In the OpenAI/Ollama path, cache reading is included in the input: 125,088 − 95,780 = **29,308 input tokens without cache reading**, approximately 76.57% of input reused. Total = 125,088 + 4,838; cache hit is not added again. The panel counts tokens, not cache requests.

This is accumulated usage between calls, not the current context size nor the number of words written. OpenHands resends instructions, tool definitions, history, and results to each call. A repeated prefix can leverage the KV state that Ollama already calculated; new generation continues to do inference. Neither the number of cached tokens nor the local cost 0 prove a percentage of time, GPU, energy, or money savings.

## Real Check in Ollama

Two identical synthetic calls, directly to `/v1/chat/completions` of the installed local Ollama, reported:

| Call | Input | `prompt_tokens_details.cached_tokens` | Output | Total |
| --- | ---: | ---: | ---: | ---: |
| 1 | 1,624 | 1 | 8 | 1,632 |
| 2 | 1,624 | 1,623 | 8 | 1,632 |

Only the numerical usage was read for the report. This verifies that **this installation actually reports prefix reuse**, not retrospectively validates the 95,780 units of the entire conversation. Direct calls do not pass through LiteLLM and, by design, do not appear in its counters.

The code [Ollama v0.35.1](https://github.com/ollama/ollama/blob/v0.35.1/openai/openai.go) copies `PromptEvalCachedCount` to `usage.prompt_tokens_details.cached_tokens`. The [SDK OpenHands v1.49.6](https://github.com/OpenHands/software-agent-sdk/blob/v1.49.6/openhands-sdk/openhands/sdk/llm/utils/metrics.py) documents that the LiteLLM/OpenAI path includes cached reads within `prompt_tokens`.

## Scopes That Explain the Discrepancy

The previous snapshot of Prometheus/Grafana was 30 input tokens and 4 output tokens, with two usage observations and three requests to the proxy, including an authentication rejection. It is not a fixed expected value nor the total of OpenHands. The proxy counters cover all calls that effectively pass through it, from the start of its sender; they do not incorporate the history of direct calls or previous calls before its installation.

The effective configuration of a conversation may retain the path with which it was created, even if the general profile is edited. A read-only diagnostic was added:

```bash
mise exec -- task openhands:usage:check CONVERSATION_ID=a8ee8912-0e52-49d0-9cfc-03396d266920
```

Shows the current path and numerical usage; does not print messages, keys, or history. The current path alone does not demonstrate the paths of all previous calls. The host's later output confirmed `direct Ollama`; the final tracking documents this finding. The paths of all historical calls are not deduced from the current path.

The previous hypothesis about an incorrect sum of samples is discarded as an explanation for **this capture**: it was OpenHands. The verified Grafana cards use instantaneous queries and `lastNotNull`, not `sum_over_time` of counters. A deliberately incorrect sum gave 57,575, but never demonstrated a failure in the provisioned panels.

## Cache Implementation

The LiteLLM OTel callback v1.104.0 does not correctly cover the nested field of Ollama: its experimental code looks for higher fields as `cache_read_input_tokens`. The [native Prometheus callback](https://github.com/BerriAI/litellm/blob/v1.104.0/litellm/integrations/prometheus.py) does read `prompt_tokens_details.cached_tokens`.

This existing callback is used, restricted to two token counters and label `model`. The Prometheus receiver of the Collector reads `/metrics/` with Bearer authentication via internal network, retains only those counters and the allowed local model, removes free labels, and delivers to Prometheus. The key remains outside of Git/CloudDrive and is not exported as an attribute. OTel is preserved for input/output/traces; no runtime adapter or span-derived accumulator is added.

New panels in Platform Overview and LLM Cost/Routing: Accumulated Cache Hit/Write, period increments, tokens/s, percentage of reused input, and internal scrape status. The cache is presented as a subset of Input, without adding it to the total.

The native exporter emits these series when there are positive values. **No data does not mean zero or cache disabled**. In particular, the OpenHands interface may show Cache Write 0 by default even if Ollama does not report writing. The numbers from the capture are not imported as live metrics nor is historical consumption automatically recovered.
